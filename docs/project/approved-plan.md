# Sumika 新版总实施计划：Harness 优先的 Codex 日用平替

来源：本任务中用户以「PLEASE IMPLEMENT THIS PLAN:」提交的完整计划。以下保留正文；界面注释指令不作为产品需求。没有可核实消息 ID 或消息时间，不虚构这些字段。

## 目标与原则

新版从独立分支重新开始，首版使用最新已验证的 DSH 作为默认 Harness，先达到 Codex 日常开发替代能力；架构通过 Harness 中立接口保留未来更换 DSH 的可能。

DSH 接入尽量融入其原生项目、会话、工作区、任务、Skills、MCP 和 Web UI 能力，新增能力的核心逻辑保持独立。

实现功能时，优先复用 DSH 社区插件或高质量开源项目；只有没有合适方案时才自行实现。

## 阶段总览

### 阶段 0：新版项目与连续性基础

目标：建立可交接、可恢复、可审计的新项目骨架。

- 创建独立 orphan 分支，不继承旧版源码。
- 固定初始 DSH 版本、安装布局、profile 和回滚方式。
- 建立 Harness 中立的适配接口。
- 保存用户需求原文、来源、时间顺序和当前有效状态。
- 保存总计划、阶段计划、决策、变更原因和验收条件。
- 保存已实现、部分实现、未实现、受阻、已验证和待验证状态。
- 保存模型交接记录，使新模型只依靠项目记录即可继续工作。
- 记录项目数据备份与恢复能力，首版暂不考虑加密。
- 建立 Git checkpoint、恢复点和变更记录规则。

验收：新模型不读取历史聊天，也能找回当前目标、计划、进度、阻碍和下一步。

### 阶段 1：Harness 中立契约与安全边界

目标：让 Sumika 的核心逻辑不依赖 DSH 私有实现。

- 定义统一的 Harness、会话、任务、工作区、工具调用、事件、取消和恢复对象。
- 为 DSH 编写薄适配器。
- 区分受管 DSH 实例与外部未核验端点。
- 建立实例身份、请求版本、会话和执行步骤绑定。
- 所有写操作经过统一授权和审批入口。
- 未知状态默认停止，禁止通过重试、重规划或伪造事件绕过授权。
- 保留费用、模型、凭据和外部操作的现有安全边界。

验收：替换适配器不会改动核心任务状态机；普通 HTTP 或伪造字段不能获得可信授权。

### 阶段 2：DSH 发行锁定与真实能力验收

目标：确认 DSH 版本确实能承载首版日用开发闭环。

- 锁定具体 DSH 发布版本和依赖文件。
- 使用独立安装目录与 profile。
- 验证 Web UI、会话、历史、工作区、文件工具、终端、测试、Plan、Skills、MCP、子 Agent、取消、恢复和事件流。
- 验证必要社区插件的加载和版本兼容。
- 对 DSH 协议变化使用适配层处理，不把方法名和路径散落在业务代码中。
- 保留旧版本可回退，不自动切换未验收候选版本。
- 每次 DSH 更新都执行协议探测、真实临时项目操作和回归测试。

验收：在隔离 profile 中完成一次真实临时项目的读取、修改、测试、取消、恢复和结果查看。

### 阶段 3：Codex 日用开发平替

目标：首版可以承担真实日常开发任务。

- 使用 DSH 原生 Web UI，不重写 Sumika UI。
- 支持代码搜索、阅读、修改、删除和新增。
- 支持终端命令、测试、构建和日志查看。
- 支持 Plan/Execute、任务拆分、子 Agent 和代码审查。
- 支持用户确认、取消、暂停、重试和恢复。
- 支持项目、工作区、会话和任务组织。
- 支持 Skills、MCP 和外部工具接入。
- 支持上下文压缩与连续性记录协同工作。
- 任务完成后记录成果、验证证据、剩余问题和下一步。

验收：在真实项目中完成一个中等规模开发任务，包含规划、修改、测试、审查和恢复；过程中不丢失需求和授权边界。

### 阶段 4：连续性记录正式接入

目标：让需求和进度记录成为日常工作流的一部分，而不是独立手工文档。

- 在任务开始时记录用户需求原文和当前目标。
- 在计划变更时记录新旧计划、原因和受影响任务。
- 在阶段结束时记录实现、验证、未完成项和限制。
- 在上下文压缩、会话重启和模型切换时生成可恢复交接。
- 将记录与项目、任务、会话和 Git checkpoint 关联。
- 支持查询当前状态、历史决策、需求来源和下一步。
- 记录不确定信息，不把模型推断写成用户确认需求。
- 对原文、摘要、代码、diff 和角色附言保持边界。

验收：中途更换模型后，模型能从记录继续任务，不重复已完成工作，也不误把未验证结果当作完成。

### 阶段 5：首批扩展——办公文件与桌面助手能力

目标：在 Codex 平替稳定后，扩展日常桌面生产力。

优先复用 DSH 插件或开源项目：

- 文档、表格、演示文稿和 PDF 的读取、创建、修改。
- OCR 和截屏翻译。
- 通用桌面软件观察、点击、输入、快捷键和窗口控制。
- 可按需添加、排序、移除的能力模块。
- 同一能力切换不同实现，例如不同 OCR 或语音引擎。
- 一次性、每日、每周定时任务，区分提醒与真正执行。
- 网页 AI 咨询，来源数量不设固定上限。
- 咨询页面统一在内置浏览器中管理。

不在首批实现自动选模、复杂费用路由、免费权益自动领取和 macOS/Linux 支持。

### 阶段 6：首批扩展——角色系统基础

目标：建立角色陪伴的可用基础，不一次实现完整虚拟生活。

- 工作模型与角色模型分开配置。
- 保留角色上下文注入，但角色口吻和附言不得污染开发原文、代码、diff 或成果正文。
- 调研并比较 DSH 插件和开源长期记忆方案，按中文回忆、事实更新、多角色隔离、误召回、延迟、成本和迁移能力选优。
- 导入角色卡、2D/3D 模型、语音模型和场景资源。
- 世界书、背景设定库和角色主题配色。
- 语音交流及经授权的屏幕、摄像头感知。

### 阶段 7：长期角色与设备愿景

按实际验证结果逐步实现：

- 陪看视频、观看和评论游戏。
- 角色实际参与游戏。
- 虚拟房间、固定或跟随摄像头视角、自主生活。
- 桌面壁纸陪伴模式。
- 多角色独立人格、模型、记忆和共同生活。
- 摄像头、传感器、遥控小车等现实设备接入。
- 远程访问与手机端。
- 项目数据备份恢复的完整用户流程。

## 复杂度与模型分工

由高能力主 Agent 负责：

- Harness 中立契约。
- DSH 协议和版本迁移。
- 授权、安全、恢复和取消。
- 数据模型与连续性记录边界。
- 插件/开源方案选型。
- 阶段验收和最终整合。

接口冻结后，可交给 DeepSeek V4.1 Flash：

- 配置读取与普通存储。
- DSH 插件包装。
- 文档、表格、PDF 等边界清晰的基础操作。
- 测试夹具、适配层样板和常规 UI 接线。
- 已确定方案的重复性实现。

## 测试与交付门槛

每个阶段都必须同时记录：

- 实现范围；
- 自动化测试；
- 真实 DSH 或真实工具验收；
- 未验证内容；
- 阻碍和回退方式；
- 下一阶段入口。

阶段完成不能只依据单项测试或代码存在；必须区分“已实现”“测试通过”和“实际可用”。

## 后续明确需求（不改写上方已批准原文）

- R-105 / R-106：新增能力使用独立功能代码，DSH 专属部分放在适配中间层；优先利用原生插件/Skill 接口。升级 DSH 或更换 Harness 时复用独立实现和数据。
- R-107：所有新增的非 DSH 原生功能，都应在设置中提供独立开关。

R-107 的实施约定：关闭后停止该功能的自动执行、专用工具暴露与上下文注入，保留数据供重新启用或恢复。开关不授予工具权限、不触发模型调用；依赖或需重启时向用户说明。R-108 明确本次先预留功能级开关，后续设计 UI 时接上设置页。P4 提供 enabled 配置并验证启停行为；设置 UI 仍待实现。上述开关语义属于实现约定，需求原文以 requirements.json 为准。

- R-109：不修改 DSH 上游源码。通过其原生插件/Skill/MCP 等扩展接口接入，DSH 专属适配与独立功能实现分离；不得直接补丁修改安装包、node_modules 或维护 Sumika 专用上游分叉来实现功能。可正常升级到经过验收的上游版本。接口不足时记录缺口并调整扩展方案，不以修改上游源码绕过。
- R-110 / F-001：未来增加供 Agent 排障使用的独立诊断日志扩展。当前已有原生日志，但缺少统一关联与查询，故保留此计划。优先复用 DSH 日志/事件及高质量开源组件，补充 Agent 可用的查询和故障证据提取；不建设面向用户的日志看板，不要求用户亲自审阅代码或日志。具体范围、验收与复用调研见 agent-diagnostics-plan.md。本次仅新增计划，未实施。

- R-111：P4 优先精简重复原生能力，评估复用现成方案。当前先停止重复采集原生助手/工具日志，并跳过无新增有效记录的同步；保留原文、报告、恢复边界及旧数据。
- R-112：长期记忆优先使用现成社区插件或开源实现，先形成可用基线，再通过实际效果和能力比较择优替换。仍归 P6，具体选择路径和评测条件见 long-term-memory-plan.md；不先自研记忆引擎。
