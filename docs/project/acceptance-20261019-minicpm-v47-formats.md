# MiniCPM-V 4.7 规格/格式对比（2026-10-19）

目标：在笔记本 GTX 1060 6GB / 16GB RAM 上，比较 MiniCPM-V 4.7 的 1B 与 35B-A3B 规格、GGUF 量化格式，找出最适合日常视觉/短文本的版本。全部使用合成图片和合成文本，未读取用户内容。

## 测试矩阵

| 规格 | 格式 | 体积 | 启动 | 视觉 | OCR | JSON | 改写约束 |
|---|---|---:|---:|---:|---:|---:|---|
| 1B | Q4_K_M | 0.63GB | ~20s | 1.62s，正确 | 0.79s，正确 | 0.12s，正确 | **丢失“不要改时间”** |
| 1B | Q5_K_M | 0.70GB | ~2s | 4.73s，正确 | 2.06s，正确 | 1.01s，正确 | “时间不变”，保留 |
| 1B | Q8_0 | 1.01GB | ~2s | 4.07s，正确 | 2.33s，正确 | 0.82s，正确 | “时间不变”，保留 |
| 1B | F16 | 1.89GB | ~2s | 3.48s，正确 | 3.23s，正确 | 1.20s，正确 | “时间不变”，保留 |
| 35B-A3B | IQ3_XS + no-think | 13.49GB | ~30s | 9.85s，更详细 | 5.25s，正确 | 1.08s，正确 | “时间不变”，但“五十块”→“50元” |

计时受显存/缓存影响，不代表严格吞吐基准。

## 关键观察

- **1B Q4 最快，但约束保持最差**：改写直接丢掉“不要改时间”，不适合任何需要保留限制的任务。
- **1B Q5/Q8/F16 质量接近**；Q8 在语法和完整度上最稳，F16 没有明显质量收益且体积接近两倍。Q8 是 1B 中综合最合适的格式。
- **35B-A3B IQ3_XS** 视觉描述更完整、OCR 正确、改写语义最好；但权重 13.49GB，必须停掉 8082/8083 才能加载，30 秒启动，单次 5–10 秒。它不适合和共享服务同时常驻。
- **35B 默认会进入 thinking**，首轮文本空正文、耗时 47–87 秒；加 `chat_template_kwargs.enable_thinking=false` 后降到 1–10 秒。文本任务必须关闭 thinking。
- **35B Q4_K_M 19.71GB 未测试**：超过 16GB 内存，预计依赖 pagefile/严重换页；不作为可部署候选。Q5/Q8/F16 35B 更大，同理。
- 1B Q8 与 8082/8083 同时在线可运行；但同题改写复用缓存时曾再次丢失“不要改时间”，说明 1B 的约束保持不稳定，不能用于提示词优化。

## 结论

| 用途 | 建议 |
|---|---|
| 日常视觉/OCR/短文本，共享服务同时在线 | **1B Q8_0**（`D:\Models\minicpm-v47\1B-Q8_0.gguf`，SSD，约 1GB） |
| 质量优先、可停共享服务、离线批处理 | **35B-A3B IQ3_XS**（`D:\Models\minicpm-v47\35B-IQ3_XS.gguf`，SSD，13.49GB，必须 `enable_thinking=false`） |
| 极速但可接受约束丢失 | 1B Q4，仅限非约束性描述 |
| F16 / Q5 | 无必要；Q8 已覆盖 |
| 35B Q4/Q5/Q8、AWQ/GPTQ/FP8/BF16 | 当前 6GB/16GB 笔记本不适用或未验证 |

“最适合”按默认日常场景判定为 **1B Q8_0**；若目标是最高质量且能接受停服务，则 **35B-A3B IQ3_XS**。

## SSD 与真实屏幕补测

- 笔记本磁盘：`F:` 是 **WDC WD10SPZX HDD**；`D:` 是 **SAMSUNG NVMe SSD**（约 98GB 空闲）。模型原先在 HDD 上，**不是 SSD**。
- 已把 `1B-Q8_0`、`35B-IQ3_XS`、35B mmproj 复制到 `D:\Models\minicpm-v47`。35B 加载时间从 HDD 的约 30 秒降到 **8.1 秒**。
- 真实渲染 UI（1280×720，含标题栏、侧栏、三张卡片、四列表格、按钮、提醒）测试：

| 模型 | 全文字 | 表格 JSON | 按钮/状态 | 观察 |
|---|---|---|---|---|
| 35B IQ3_XS | 55.8s，**完整** | 25.5s，**三行全对** | 16.0s，正确 | 质量最好，但单次 16–56 秒 |
| 1B Q8_0 | 6.4s，漏“任务/记忆/设置”和“本地服务在线” | 4.6s，**三行全对** | 4.0s，正确 | 表格/按钮可用，全文字不完整 |

结论：真实屏幕 OCR 上 **35B 完整但慢，1B Q8 快但会漏非表格文字**；若只要表格抽取，1B Q8 已够用。

## LES 编译可行性

- 笔记本当前没有 `cmake`、`cl`（MSVC）、`nvcc`，只有 `git`；无法直接构建 `llama.cpp-omni`。
- 已克隆并检查 `OpenBMB/llama.cpp-omni`：源码确实包含 MiniCPM-V 4.7 图和 LES 代码，但 LES 运行需要 `--moe-experts` 的 **expert-major manifest/sidecar**（`schema_version 1`、`experts_kind`、`layout` 等）和 `--moe-slot-bank`；公开 HF 仓库只看到 `mix_q3gud_im.gguf` 与 `tensor-types.txt`，没有现成 manifest，需额外 repack 工具。
- 官方 3GB/17.39 token/s 数据是 iPad M4 的端侧结果；Windows CUDA 构建没有现成发布包，需安装 CMake + VS Build Tools + CUDA 工具链后自行编译，仍不能保证 6GB 笔记本达到同样效果。
- 结论：**LES 目前不是“装个包就能用”**；缺工具链和 expert-major 资产，暂不作为可交付方案。

## 边界

- 合成图只有蓝框/橙圆/一行文字，OCR 只有三行；不代表真实屏幕、复杂表格、公式、长文档。
- 35B 未接产品，只做临时 llama.cpp 服务；测试后已停止，8082/8083 恢复，8084 未监听。
- 1B Q5/Q8/F16 复用 8083 的 mmproj；35B 使用其专用 mmproj。
- 真实屏幕是受控本地 HTML 渲染，不是用户桌面；没有读取用户窗口或私人内容。
- 没有测长上下文、多图、视频、工具调用；这些不能由本结果外推。
