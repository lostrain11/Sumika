# 阶段 1：Harness 中立契约与边界

`contracts.py` 定义实例、工作区、会话、任务、工具调用、事件、取消回执与恢复对象。`Execution` 只依赖 `Harness` 协议，不含 DSH 路径或方法名；第二个内存 Harness 的测试使用同一派发与恢复逻辑。

## 可信宿主与原生 DSH

DSH 启动器先核验发行文件摘要和已安装 CLI 元数据，再启动自己的 Node 子进程。只从该子进程 stdout 获取一次性启动 URL，换取 DSH 原生签名 cookie；通过 Windows 监听端口的 OwningProcess 核对 PID，调用前再次检查实例存活与端口归属。外部 URL 和用户填写的 managed 标记都不是适配器的接管方式。

Python 进程内部属于可信宿主；Authority 不是抵御同进程恶意代码的沙箱。调用方不能将 approve、DSH Cookie、私有 RPC 或 SQLite 写入暴露为模型工具/普通 HTTP 服务。DSH 原生 Web 使用其已有认证、同源检查与权限策略，不另造一套 UI 登录。

## 所有新增写入的调用顺序

1. 宿主根据用户授权创建 WorkBinding，包含实例、请求 ID/版本、会话和步骤。
2. 宿主审查 ToolRequest 的动作、目标和不可变参数字节，再调用 Authority.approve。参数必须包含完整写入内容、命令和工作目录；不能批准后补充可变参数。
3. Execution.dispatch 在 SQLite 写事务中检查旧步骤及未知操作，消费一次性批准，先持久化 UNKNOWN 与事件，再交给适配器。未批准、篡改或重复请求不能进入适配器。
4. 有效业务回执落盘后仅将这个操作标为完成。取消回执只表示取消已请求，不将原任务标为完成或未发送。
5. 超时、异常、进程退出或丢失回执保留 UNKNOWN。重启、更改步骤或请求版本不能绕过同一请求的未知操作。允许额外明确授权的取消，但不清除未知操作。

请求升级使旧版本批准失效；撤销使旧绑定永久失效；并发消费最多一次成功。事件只从本地派发事务产生，可按游标读取，没有公开事件注入入口。恢复只读，不从摘要/远端状态推导新授权。

## DSH 薄适配器

阶段 1 开放并真实验收 `session.create`、`session.cancel` 与只读历史检查，绑定工作区和会话。RPC 校验 type、rpcId、业务 ok 及业务结果；HTTP 200 内的错误也失败。rc.2 实际请求为 client-request → payload.args.request；协议细节仅存在 dsh.py。

通用文件、终端、模型派发和完整流式事件是 P2/P3 的原生能力验收范围。目前不提供 prompt、模型切换、凭据修改或付费 fallback 的新增入口，所以不会因空模型/失败而隐式调用其他模型。今后开放必须复用并验证 DSH 原生工具审批，不能直接给私有 RPC 加白名单。

## 可验证范围

阶段 1 验收证明新增核心与受管生命周期的契约/授权边界。没有宣称同用户恶意进程隔离、完整 OS 沙箱、活跃模型任务取消、硬费用上限、全部 DSH 工具均已验收。这些与完整日用闭环分别记录于 P2/P3，不以本轮空闲会话验收替代。
